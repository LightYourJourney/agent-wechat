# SECURITY — 隐私与安全

> 本文档说明项目处理了哪些敏感数据、如何保护它们，以及你必须了解的法律与平台条款
> 风险。**使用前请完整阅读本文档。**

## 1. 项目处理了什么数据

| 数据 | 位置 | 敏感度 |
|---|---|---|
| 数据库密钥 passphrase（32 字节） | 内存（微信进程）→ `~/.agent-wechat/passphrase.json` | 极高 |
| 聊天数据库（加密） | 微信容器目录 | 高（常规流程只做只读快照、不落盘存储；**唯一例外**是 `decrypt --out`，见下表） |
| 解密后的消息明文 | `~/.agent-wechat/tmp/`（临时）→ `index.db`（持久） | 极高 |
| 解密后的媒体明文（图片/语音 WAV/视频）与**会话时间线产物**（HTML / Markdown 明文，含引用 / 链接 / 转账内容） | `~/.agent-wechat/media/`（持久） | 极高 |
| 朋友圈正文 / 评论 / 点赞 / 媒体明文（`moments export` 产物） | `~/.agent-wechat/moments/`（持久；目录 0700、文件 0600） | 极高 |
| **例外**：`moments export --out DIR` 会把同一份朋友圈明文（含已下载的媒体）写到**任意指定目录** | `DIR`（代码尽力 chmod 0700，但不在 `~/.agent-wechat/` 之下） | 极高（用后必须手动删除；不受 Time Machine 排除与 `purge` 覆盖） |
| **例外**：`decrypt <db> --out` 调试命令会**持久**写出整库明文 | `~/.agent-wechat/<out>` | 极高（用后必须手动删除） |
| **例外**：`media export --out DIR` 会把同一份媒体明文写到**任意指定目录** | `DIR`（代码尽力 chmod 0700，但不在 `~/.agent-wechat/` 之下） | 极高（用后必须手动删除；不受 Time Machine 排除与 `purge` 覆盖） |
| **例外**：`chat export --out DIR` 会把同一份**会话正文明文**（HTML / Markdown，含引用原文与转账字段）写到**任意指定目录** | `DIR`（代码逐级 chmod 0700、文件 0600，但不在 `~/.agent-wechat/` 之下） | 极高（用后必须手动删除；不受 Time Machine 排除与 `purge` 覆盖。`chat index --out` 只写一页索引，同理） |

数据流向**默认始终在本机**：embedding、检索、MCP（stdio 传输）全部本地闭环，
不存在任何网络上传路径。媒体导出同理——pilk（进程内调用）与 ffmpeg（本地子进程）
都只做本机解码，不联网、不上传。

**MCP 信封里的消息正文（含本次新增的 `get_message_parts`）**

上面那句「不存在任何网络上传路径」说的是**本工具自身**：MCP 走 stdio，Server 不向任何服务器
发送数据。但**信封的内容会进入 Agent 会话**，因而**可能进入你所用的 LLM 上下文**——这是项目
既有的性质，不是本次新增：`get_recent_messages` / `search_history` / `semantic_search` 一直
在返回消息正文。本次新增的 `get_message_parts` 沿同一约定，按 `msg_key` 返回 appmsg 的结构化
内容，**包括转账（type 2000）的金额 `amount_desc`、备注 `memo`、双方用户名 `payer` /
`receiver` 与交易号 `transaction_id`**（凭据类字段另有剔除，见 TOOLS.md §13）。**这是刻意的、
有据的**——2026-09-16 的裁定 8：与 `search_history` 已在信封返回正文一致，**不为转账单开例外**，
不是遗漏。不想让某类内容离开本机，就不要调用会返回它的工具。

**这条出口的落点，过去没有被文档化**

上面那段说的是「内容会进入 Agent 会话」。**它的落点是磁盘上的会话转录**——
`~/.claude/projects/*.jsonl` 与 `~/.codex/sessions/`。这意味着**同一条消息在本机
至少有两份明文**：设计内的 `~/.agent-wechat/index.db`，和一份不受本项目控制的转录。

**这件事已经发生，且不可撤回。** 凡是返回过正文的 MCP 调用，内容都已经发出去了；
删本机副本不会撤回任何东西。写在这里是为了防止后来者再花一轮去「清」它。

### 零网络例外（三个）

先给出全貌：**「零网络」有三个例外**，其中第 3 条（贴纸 CDN 取件，2026-09-23 新增）
**是唯一走明文 HTTP 的**——它的详情在本节末尾单独说明。

1. **首次构建向量索引时下载模型**（既有）：`vector.FastEmbedEmbedder` 先在本地缓存
   `~/.agent-wechat/models` 里找模型，找不到才联网取约 95MB 公共资产
   （`vector.py:125` 先纯离线加载，缓存缺失才在 `:130` 回退下载）；模型就位后嵌入与
   检索完全离线（见 FAQ Q15）。它与下面这条一样，都是**入站下载**。
2. **朋友圈媒体下载**：下面详述（HTTPS）。
3. **贴纸 CDN 取件**（2026-09-23 新增）：本节末尾详述。**它走明文 HTTP**——见下。

上面那句「不存在任何网络**上传**路径」在这三条例外下**都依然成立**——被打破的是「零网络」，
不是「零上传」：流量都是**入站方向**的，本机不向任何服务器发送聊天 / 索引 / 密钥内容。
**第 2 条具体是什么：**

- **触发条件**：只有用户显式指定 `--with-media`（CLI `moments export`）或
  `with_media=True`（MCP `export_moments`）时才成立。两者默认都是 `False`
  ——不加则整次导出一个网络请求都不发。
- **目标域**：只连微信 CDN——后缀 `*.qpic.cn` / `*.video.qq.com`，加精确主机
  `wxapp.tc.qq.com`（**不含子域**）；代码里两部分都在，且**跨重定向也成立**；
  其余主机一个请求都不发（`build_url` 前置判 host，直接标「不去取」），
  请求不会被引向别处。
  - 匹配**不区分大小写**（`https://SHMMSNS.QPIC.CN/x` 通过）；末尾带点（`qpic.cn.`）被拒；
    裸域名 `qpic.cn` 本身**不在**白名单内（`*.qpic.cn` 要求至少一级子域）。
  - ⚠️ **端口不受约束**：`https://shmmsns.qpic.cn:22/x` 这类地址会通过白名单并真的向
    该端口发起连接（实测）。目标主机仍限白名单，**不构成越权**，但恶意 XML 可借此对这几台
    微信 CDN 主机做端口探测——若你对此敏感，可在网络层限制出站端口。
- **发送内容**：请求只携带微信自己签发的媒体 `token` 与固定 `User-Agent`
  （`MicroMessenger Client`），**不含本机任何聊天 / 索引 / 密钥内容**，无请求体。
- **不走代理**：一律直连，不读 `http_proxy` 等环境变量。
- **目录只读**：产物只写 `~/.agent-wechat/moments/`（或用户显式 `--out`），
  绝不写回微信目录。

**第 3 条具体是什么（贴纸 CDN 取件）：**

- **触发条件**：只有同时指定 `--kinds` 含 `sticker` **且**显式加 `--with-cdn`
  （MCP：`export_chat_media(kinds="…,sticker", with_cdn=true)`）时才成立。
  `--kinds` 的默认值**不含** sticker，`with_cdn` 默认 `false` —— 两个开关都是显式的，
  不加则整次导出一个网络请求都不发。加了 `sticker` 但没加 `--with-cdn` 时，
  贴纸一条都不导、并如实计入 `counts.sticker.missing`。
- **目标域**：只连腾讯 CDN 的 `*.tc.qq.com`（实测出现 `vweixinf.tc.qq.com` 与
  `wxapp.tc.qq.com`），**跨重定向也复查**同一个后缀判据（白名单只对第一跳成立等于没有白名单）。
- **⚠️ 明文传输，凭据明文出网**：实测 `https://vweixinf.tc.qq.com/…` 的证书
  **对主机名无效**（`CERTIFICATE_VERIFY_FAILED: Hostname mismatch`），而消息 XML 里给的
  scheme 本就是 `http`，故当前一律明文 HTTP。**请求 URL 携带该贴纸的 `filekey`——
  它会在网络上明文可见。** 这是既知且被显式接受的代价；**不要把这条描述成加密传输**。
  - 范围说明：**只实测过 `vweixinf.tc.qq.com` 这一个主机名**。另一个 host
    `wxapp.tc.qq.com` 在下面第 2 条的白名单里、其 https 行为**未实测**——所以
    「贴纸 CDN 一律不支持 https」是不准确的推广。
- **发送内容**：请求只携带该条贴纸的下载 `filekey`（在 URL 查询串里）与固定
  `User-Agent`，**不含本机任何聊天 / 索引 / 密钥内容**，无请求体。
  **不发送 `aeskey`**：实测 `cdnurl` 返回的就是明文图片，不需要它。
- **凭据不落盘**：`cdnurl` / `filekey` 只在取件那一刻从微信库现取、随函数栈帧消失，
  **不落库、不进日志、不进 MCP 信封**（贴纸 XML 不落库是结构性根治，见 spec §7.1）。
- **不走代理**：一律直连，不读 `http_proxy` 等环境变量（macOS 的系统代理会让请求超时，
  实测）。
- **校验后落盘**：下载内容按 XML 的 `md5` 属性校验，不符即判失败、**不落盘**。
- **目录只读**：产物只写 `~/.agent-wechat/media/`（或用户显式 `--out`），
  绝不写回微信目录。

## 2. 密钥如何获取（风险最集中的环节）

`bootstrap` 的原理：对微信 ad-hoc 重签名去掉 Hardened Runtime → lldb attach 微信进程
→ 在系统函数 `CCKeyDerivationPBKDF` 上下断点 → 用户在微信内重新登录触发密钥派生 →
从寄存器读取 32 字节 passphrase → HMAC 校验通过后落缓存。

**风险与性质**：

- lldb 仅在断点命中的瞬间读取一次寄存器即 detach；不修改微信行为、不接触网络协议、
  不注入代码。公开同类工具（跨平台、经大量真机验证）均采取同一原理且未报告触发风控，
  但**无官方保证**，理论上存在账号受限风险
- 重签名会修改 `/Applications/WeChat.app` 的代码签名（数据不受影响）；微信每次升级
  会还原签名，需重跑
- passphrase 缓存文件 `0600` 权限，仅当前用户可读；它**不会**被写入日志或错误信息

**替代方案（未采用，供了解）**：关闭 SIP 可绕过重签名，但影响整机安全面，代价远大于
收益；纯文件解析路线已通过 HMAC 验证系统排除（见 ARCHITECTURE.md §3.2）。

## 3. 只读保证与账号隔离

- **只读**：代码不存在对微信容器目录的写路径；解密用 db+wal+shm **快照**进行，
  即使微信正在写入也不受影响
- **账号隔离**：数据目录按 `wxid` 物理隔离；passphrase 按账号分键；读取/导出默认
  操作**当前登录账号**，可用 `--account` 显式指定本机已有账号。**技术上无法访问
  未在本机登录过的他人账号数据**（没有其密钥）
- **权限边界**：不使用辅助功能权限；不需要关闭 SIP；MCP 走 stdio，不监听任何网络端口

## 4. 明文数据的存储与访问控制

全量导出会在 `~/.agent-wechat/index.db` 形成**一份完整的、可检索的明文聊天档案**——
这是本项目最大的数据资产，也是最大的风险面。已落实的控制：

| 控制项 | 措施 |
|---|---|
| 文件权限 | `~/.agent-wechat/` 全目录 `0700`，passphrase 缓存 `0600`（仅当前用户可读） |
| 全盘加密 | 索引明文依赖 **FileVault**（**建议开启**，见 INSTALL.md）；未开 FileVault 的机器不建议使用本项目的导出功能。⚠️ **代码不校验也不阻断**，建议自行用 `fdesetup status` 确认 |
| 备份排除 | 首次使用时代码自动执行 `tmutil addexclusion ~/.agent-wechat`（可用 `tmutil isexcluded` 验证）；失败时请手动执行，防止明文档案绕过 FileVault 进入备份盘 |
| 临时文件 | 解密明文仅在 `tmp/`（0700）短暂存在，单分片、用后即焚——**按消息查媒体归属（`media locate` / `get_message_media`）的语音本体判定也走这一条**；唯一例外是 `decrypt --out` 显式导出的明文库（见上表） |
| 传输 | MCP 走 stdio；无网络监听、无云同步路径 |
| 销毁 | `agent-wechat purge --all --yes` 清除**整个 `~/.agent-wechat/` 超集**——不只是「密钥 + 索引」，还包括 `media/`、`moments/`、`models/`、`tasks.json`、`tmp/` 等全部产物；不加 `--yes` 只预览，删完给出残留核查。手工 `rm -rf ~/.agent-wechat` 仍是等价后备 |
| 按会话销毁 | `agent-wechat purge --chat <会话> --yes` 只删该会话在**本工具里的副本**（索引行、向量、appmsg 部件、媒体引用、群成员显示名、`media/<会话md5>/`），并把它们的 `msg_key` 逐条写进 `exclusions.db`——那批内容不会因重导复活（`export --full` / `appmsg rebuild` / `media rebuild-refs` / 名册重建四条路都在写入端被拦），而删除之后新来的消息照常进索引。**微信容器一个字节都不动**（只读红线不变）；**朋友圈导出不在范围内**（`moments/` 是一份 HTML 装所有人，不按会话分目录） |
| 会话转录 | `~/.claude/projects/`、`~/.claude/file-history/` 等承载内容的位置**已移出 Time Machine 备份范围**（`tmutil addexclusion`），配置与插件照常备份。**注意：这是"移出备份"，不是"清除"——转录本身仍在盘上** |

> **按消息查媒体归属**（`media locate` / MCP `get_message_media`）**不新增任何例外**：不联网、
> 不写微信目录、不写产物根。但它**不是「零磁盘活动」**——判定语音本体要解密 `media_*.db`，
> 明文只在 `tmp/`（0700）短暂存在、用后即焚（即上表「临时文件」那一行的机制，本条不改变它）。

> **`exclusions.db` 是唯一不可重建的产物，且它的保证边界要说准**：其余产物都能重来（索引
> ≈2.5–3 小时、密钥要重新 bootstrap、`media/` 要联网重抓），排除清单不能——它没了，`purge --chat`
> 删掉的内容下次 `export --full` 就会回来。它**活过** `purge --index`（重建索引后排除仍生效），
> 但**活不过** `purge --all`（全清就该什么都不剩，CLI 会当场报出有多少条排除随之失效）。
> 而这条命令保证的是「索引里没有存活行 + 它们的 `msg_key` 进了排除清单」，**不是「字节层面
> 不存在」**：`secure_delete` 只清 SQLite 自己释放的页，vec0 的 `preview` 列装的是相邻消息的
> 正文——chunk 没整块清空时，把 `index.db` 连同 `-wal` 读成字节去 grep，仍能在活跃页里命中它
> （**不是**本工具的检索还能搜到：索引查询里它已经没有了）。要字节级清除只能 `purge --index`
> 后重跑 `export`（实测与取舍见 `内部设计记录`
> §2.2b / §5.7）。

**§6 里说的「§4 的清单」就是这七条**（上面「备份排除」与「会话转录」两行覆盖的路径；
仓库外复查判的就是「命中的顶层位置有没有落在这七条**之外**」）：

`~/.claude/projects`、`~/.claude/file-history`、`~/.claude/plans`、`~/.claude/history.jsonl`、
`~/.claude/bash-commands.log`、`~/.claude/cost-tracker.log`、`~/.codex/sessions`。
**这七条现均在 Time Machine 排除范围内**（2026-10-10 实测），**但转录本身仍在盘上**
（见上表「会话转录」行）；`~/.claude/plugins`、`~/.claude/skills`、`~/.codex/plugins`
**不在**清单里，仍是 `[Included]`——粒度判据是「承载对话内容的目录出备份，配置与插件照常备份」。

**其中 `~/.claude/bash-commands.log` 这条排除是脆的，不是一次做完就完事。** 它是活跃日志：
Time Machine 的排除是绑在 **inode** 上的扩展属性，文件一旦被重建（换了个 inode），排除就
随旧 inode 一起消失。本机实测发生过一次——该文件 2026-09-30 14:42:59 被重建，排除当场失效，
直到 10-10 复查才发现。所以这条要**定期复查、丢了重做**：

- 判据：`tmutil isexcluded <路径>`（答 `[Excluded]` / `[Included]`）；
  **不要用 `xattr -p com_apple_backup_excludeItem <路径>`**——真实属性名带
  `com.apple.metadata:` 前缀，短名恒返回「无」，拿它判会把已排除的路径读成没排除；
- 补做：`tmutil addexclusion <路径>`。

**用户侧建议**：

- 不要把 `~/.agent-wechat/` 移入 iCloud/Dropbox 等同步目录
- 蒸馏产物（JSONL 等）同样敏感，用完即删，不要进入任何同步/共享路径
- 不在聊天内容中出现的场合（屏幕共享、演示）运行 `recent`/`search`

## 5. 法律与平台条款风险（请务必知悉）

- **平台条款**：解密本地数据库、读取进程内存大概率违反《微信软件许可及服务协议》
  的相关条款
- **执法先例**：2025-10-20，同类开源项目 sjzar/chatlog 作者收到微信官方函件后
  删除全部代码；更早的 Memotrace、wechatbackup 遭遇相同命运。被发函的直接触发因素是
  **公开仓库分发**——个人自用与公开发布的风险量级不同，但"规避技术保护措施"的
  法律定性本身存在争议，**风险不为零**
- **本项目的边界**（也是对使用者的要求）：
  1. 仅处理**本机本人已登录**账号的数据；不得用于获取他人数据
  2. 仅本地使用：**不公开分发代码、不打包传播、不撰写公开教程**
  3. 导出数据不对外提供，不接入任何外部服务
  4. 从本项目取数的仓库**应装同一套提交拦截**（`security/scan.py` + 两个钩子，
     见 `security/README.md`）。注意钩子**不入库**：装在该检出的**共享 hooks 目录**
     （`git rev-parse --git-common-dir` 下的 `hooks/`，主检出与它的所有 worktree 共用），
     换 clone 或换机器要重装。

## 6. 出口清单

本项目的敏感数据可能离开本机的**全部**路径，逐条列明「有没有机制管」。
**没有机制的那几条，就是需要人盯着的。**

| # | 出口 | 机制 |
|---|---|---|
| 1 | `--out DIR` 导出（`moments` / `media` / `chat export` / `decrypt --out`） | **无**。明文写到任意目录，不受 Time Machine 排除、不受 `purge` 覆盖，**只靠人记得删**。刻意不加自动排除：一次性目录加上排除只会留下悬空配置 |
| 2 | **git 提交**（含提交信息） | `pre-commit` + `commit-msg` 两个钩子，命中即拦。**这是本仓库唯一反复复发过的出口（2026-09-13 / 09-17 / 09-27 三次）**。⚠️ **两个钩子都不入本仓库**（它们写在共享 hooks 目录里，不受版本控制），**每个 clone / 每台机器都要按 `security/README.md` 重装**。本机**已装**（`.git/hooks/` 下，2026-09-29 装上，带 `+x`，内容即 `scan.py --staged` / `--text`）；但**换了 clone 或机器，这一行的机制就回到零**，直到重装——别把「本机已装」读成「仓库自带」 |
| 3 | 备份 | 承载内容的位置已 `tmutil addexclusion`（见 §4），**当下七条全在排除范围内**。⚠️ 其中 `~/.claude/bash-commands.log` 是**活跃日志**：文件重建后排除随旧 inode 一起丢失（实测发生过一次），**要定期用 `tmutil isexcluded` 复查、丢了就 `tmutil addexclusion` 重做**。**清单是短的、人工确认的**——不要照抄扫描输出（扫描会把第三方插件夹具也列进来） |
| 4 | `/tmp` | 一次性清理，不改配置。系统重启也会清 |
| 5 | MCP 信封 → LLM | **无机制，且已不可撤回**（见 §1） |

**自动层的覆盖边界**：`security/scan.py` 认四种**形状**——`wxid_*`、`*@chatroom`、
手机号、本机路径（`/Users/<第一段>`；2026-10-12 补，守的是 CONTRIBUTING §4 那条
「本机绝对路径不得入库」）。**它扫不到**自定义微信号（alias）、群名、备注名、聊天正文
片段、导出的时间线与媒体明文。这不是实现遗漏，是形状扫描的原理边界：**能枚举的只有形状，
枚举不了的是意义。** 内容那一层只能靠人工审查与 §4 的位置控制。

路径形自身另有两条**已知漏面**（刻意留的，写在这里免得被读成全覆盖）：**非 ASCII 用户名**
（字符集是 ASCII）与**小写的 `/users/…`**（不做大小写折叠——折叠会拿 `/users/<id>`
这类 URL 片段换假阳性，而路径形**没有豁免清单这条退路**，假阳性只能靠改写文字消化）。
它的两个例外（`.mcp.json` / `.codex/config.toml`，见 CONTRIBUTING §4）**只豁免路径形**，
其余形状在那两个文件里照扫。

⚠️ **另有一条与上面不同性质的边界：二进制 / 非 UTF-8 文件根本没有被检查。**
`--all` 读不出 UTF-8 就跳过；`--staged` 对二进制文件**一行都不扫**（git 不为二进制给新增行），
只在 stderr 打一句点名警告（给出文件名，说明它没被检查），**退出码不变**。
这和「形状扫描看不见意义」是两回事——那句说的是**读了也未必看得懂**，这句说的是**压根没读**。
**不要把自动层读成「连二进制也扫过一遍、干净」。**

生成的依赖锁（`uv.lock`）**整份跳过**（`--all` 与 `--staged` 同一条规则）：内容是第三方包
元数据，实测它单独贡献 47 处手机号形假阳性（PyPI URL 的十六进制摘要里的 11 位数字串）。

**复查（定期做）**：跑一遍
`grep -rlIE 'wxid_[A-Za-z0-9_-]{4,}|[0-9]{6,}@chatroom' ~/.claude ~/.codex`，
**只看命中的顶层位置有没有落在 §4 的清单之外**——**不要照抄输出**（实测：它会列出
上千条路径，且会把第三方插件的夹具算进来）。扫描器本身**只管仓库内**。

**⚠️ 这条复查与 `/tmp` 的验收都只用两种形状，刻意不含手机号，也不含路径形。**
不含手机号是执行期实测：那版在 `/private/tmp` 单目录命中 **1000 个以上文件**（绝大多数落在
别的项目 Rust 构建树的 UUID 段、浮点字面量、整数常量中间），而 `wxid_` 精确命中 6。
不含路径形是同一个道理，而且量级更大：**实测 `~/.claude` 一个目录就有 15,675 个文件**
命中该形态（2026-10-12；口径 `/Users/` 后接一段非 `you` 的成分）——那些目录里到处是工具
输出**引用本机路径**，会话转录里每条命令、每次报错都带一条。**形状的价值取决于它在哪里
用**：路径形只在仓库内（`--staged` / `--all`）成立。**验收判据只能写「这两种
形状为 0」——写「扫描为 0」这种无条件说法，就是在宣称一件照原样不可达的事。**
