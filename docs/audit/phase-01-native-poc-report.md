# Phase 01：性能优化原型与原生代码（Rust）对照报告

> 日期：2026-11-23 ｜ 基线提交：`97b78dc` ｜ 原型代码：[`spike/phase01/`](../../spike/phase01/README.md)
> （独立实验，**`src/`、`pyproject.toml`、`uv.lock` 均未改动**）

## 0. 结论

1. **不引入 Rust。** 实测里唯一能写成原生代码的热点是导出时的逐行解码。用 PyO3 做了一版
   能正确运行的原型，第一版比 Python 还慢 10%，优化后也只快 1.26 倍，**每次全量导出省 0.24 s，
   不到导出总时长的 1%**。原因是每行的主要工作（zstd 解压、UTF-8 解码、生成 Python 字符串对象）
   在 Python 里本来就跑在 C 代码上，换成 Rust 也省不掉。
2. **四项纯 Python 改动的收益已在真实数据上测得，结果与现状逐字节一致：**

| 场景 | 现状 | 原型 | 倍数 | 正确性 |
|---|---|---|---|---|
| CLI `recent`（端到端进程墙钟） | 12.15–12.18 s | 0.57–0.70 s | **约 18 倍** | stdout 逐字节相同（3 轮） |
| MCP 常驻：`recent_messages` 第 2 次起 | 中位 0.64 s，最大 4.22 s | 中位 0.18 s，最大 0.30 s | 3.5 倍 | 输出逐字段相同 |
| 全量导出（77.8 万条） | 71.3 s | **34.9 s** | **2.0 倍** | 消息表一致；FTS 抽查 400 个查询共 169 万次命中，0 处不一致 |
| 向量构建 | 29.4 条/s，**峰值 RSS 5.95 GB** | 145.7 条/s，峰值 RSS 474 MB | **5.0 倍速度 / 内存降为 1/12.6** | 余弦 ≥ 0.99999988 |

第 3 行由两项改动叠加：进程内解密（71.3 → 62.9 s）和 FTS 批量重建（63.7 → 34.9 s）。

## 1. 选题：为什么选这几项

依据是 Phase 00 剖析的耗时排序，同时给「换原生代码」留一个对照组：

| 候选 | 选择理由 | 原型 |
|---|---|---|
| tmutil 10 s 超时 | 在线读取 82% 的时间花在这里 | `bench_tmutil.py`、`aw_proto.py` |
| 整库 `sqlcipher_export` | 在线读取剩余时间的大头；外部二进制依赖 | `inproc_sqlcipher.py` |
| 嵌入批大小 | 向量构建（全量 2.5–3 小时）的主瓶颈 | `bench_embed.py` |
| FTS 逐行触发器 | 导出时间的大头 | `bench_fts.py` |
| **逐行解码（对照组）** | 导出里唯一成块的纯 Python 计算，最可能值得写成原生代码 | `native_decode/`（Rust/PyO3） |

ISAAC64、XOR 这类微热点没有做原型：Phase 00 已经说明，用 Python 内建的 `bytes.translate`
或大整数 XOR 就能达到 C 速度，而且对用户可感知的耗时影响很小。

## 2. 原型设计

### 2.1 进程内 SQLCipher（`spike/phase01/inproc_sqlcipher.py`）

- **接口**：`open_encrypted(db, passphrase) -> Connection`（上下文管理器），返回对象的行为与 `sqlite3.Connection` 对齐。
  快照仍复用 `decrypt.snapshot`，微信目录零写入。去掉了「把整库导出成明文」这一步：查询只解密实际读到的页。
- **异常翻译**：`sqlcipher3.*Error` **不是** `sqlite3.Error` 的子类。连接代理和游标代理把它们翻译成同名的
  `sqlite3` 异常，项目里 73 处 `except sqlite3.*` 不用改。
- **打开即校验**：只执行 `PRAGMA key` 不会验证密钥，所以打开后立刻读一次 `sqlite_master`；
  密钥不对就抛项目的 `DecryptError`，报错文案里不回显密钥。
- **密钥缓存**：按（库路径, salt）在进程内缓存 PBKDF2 结果。MCP 常驻进程每个库只算一次（每次 51 ms）。
- **接线**：`install()` 在运行期替换 `decrypt.decrypted` 和 `decrypt.open_plain`。项目里 5 处
  「`decrypted` + `open_plain`」调用点（reader / media×2 / moments / cli）不改一行就整体切到新路径，
  Phase 02 落地时的改动面也就是这 5 处加 `decrypt.py`。

### 2.2 FTS 批量路径（`bench_fts.py`）

首次或 `--full` 导出时，在每次建连后删掉 messages 的 3 条 FTS 触发器（ai/ad/au）；
导出完成后重新执行 `SCHEMA` 恢复触发器，再做一次 `'rebuild'`。
**ad/au 两条也必须去掉**：导出过程中会有 UPDATE（例如会话名自愈），触发 au 去 'delete' 一行从未进过索引的记录，会把 FTS 写坏。

### 2.3 嵌入批大小（`bench_embed.py`）

只改 fastembed 的**内部** `batch_size`（`vector.BATCH` 在调用 embed 时才读取），flush 大小单独设。走的是真实 `build_index` 管道（嵌入 + sqlite-vec 写入）。

### 2.4 Rust 对照组（`native_decode/`，PyO3 0.30 + zstd 0.14，abi3-py312）

- **对象**：`reader._decode_content`（zstd 解压 + UTF-8 解码）加上 `_decode_row` 里的群消息前缀剥离。
- **两种调用粒度**：`decode_one` 每行调用一次；`decode_rows` 每张表调用一次，解码和剥前缀都在 Rust 里完成。
- **地板测试**：`noop_one` / `noop_rows` 把同样的数据交给原生函数但什么都不做，用来单独量出跨语言调用本身的成本。
- **语义对齐**：只解 zstd 的**第一帧**（与 python-zstandard 的 `decompressobj` 一致）；帧不完整时报错；非法 UTF-8 替换成 U+FFFD。

## 3. 结果明细

环境：Apple M3（8 核）/ 16 GB；真实账号，36 个库共 984 MB，约 77.8 万条消息。基准期间 load average 2–9。
全量导出和 FTS 的对比读的是**同一份 APFS 克隆冻结源**：首轮没有冻结时，因为微信在两次导出之间收到了新消息，摘要出现了不一致，冻结后一致。

### 3.1 读取路径（`bench_read.py all`，`results/read_all.json`）

| 项 | 现状 | 原型 |
|---|---|---|
| 逐库逐表全量读取（36 个库 / 1,763 张表 / 4,808,758 行） | 15.3 s | 10.9 s |
| └ 一致性 | — | **36/36 个库的摘要全部一致** |
| `recent_messages`（消息最多的 3 个会话 × 5 次，limit=50）首次调用 | 3.40 s | 0.67 s |
| └ 常驻进程中位 / 最大 | 0.64 / 4.22 s | 0.18 / 0.30 s |
| └ 峰值 RSS：自身 / 子进程 | 62 / 13 MB | 74 / 2 MB |
| 全量导出（778,451 条） | 71.3 s | 62.9 s（−12%） |
| └ 峰值 RSS：自身 / 子进程 | 85 / 13 MB | 101 / 2 MB |
| └ 产物（messages / media_refs / display_names / FTS 命中） | — | **全部一致** |

**修正 Phase 00 的一处估计**：全量导出要扫描每个库的每一页，进程内解密并不能少解密页，
只省掉了「写明文副本再读回来」这一步，所以收益是 −12%，不是 Phase 00 估的「解密降到 < 1 s」。
**在线读取（只读少量页）才是这项改动的主要受益场景。**

### 3.2 端到端 CLI（`aw_proto.py`，真实进程，**没有**对 tmutil 打补丁）

`recent <群聊> -n 20`：现状 12.18 / 12.17 / 12.15 s，原型 0.70 / 0.57 / 0.68 s（含 `uv run` 自身开销），三轮 stdout 逐字节相同。

### 3.3 tmutil（`bench_tmutil.py`）

| 方式 | 耗时 |
|---|---|
| 现状：对已排除的目录执行 `addexclusion` | 10.01 s，**两次都超时** |
| 原型：先 `isexcluded`，已排除就跳过 | 0.05–0.19 s |
| 原型：全新目录（确实需要排除） | 1.08 s；第二次 0.08 s |

### 3.4 FTS 批量重建（`bench_fts.py`，`results/fts.json`）

| 方式 | 耗时 | 峰值 RSS |
|---|---|---|
| 触发器逐行（现状） | 63.7 s | 99 MB |
| 批量灌入 + rebuild | **34.9 s**（灌入 27.6 s + rebuild 7.3 s）→ **−45%** | 101 MB |

正确性：消息表一致；两边 `integrity-check` 都通过；`secure-delete` 配置在重建后仍然生效；
3 条触发器都已恢复；随机抽 400 个子串查询，共 1,692,716 次命中，**0 处不一致**。

### 3.5 向量构建（`bench_embed.py 8000`，`results/embed.json`）

取前 8,000 条消息，其中 6,569 条可嵌入。

| fastembed 内部批 / flush | 耗时 | 速度 | 峰值 RSS | 与基线的最小余弦 |
|---|---|---|---|---|
| **256 / 256（现状）** | 223.7 s | 29.4 条/s | **5,953 MB** | — |
| 16 / 256 | 57.1 s | 115.0 | 692 MB | 0.99999988 |
| 16 / 1024 | 57.6 s | 114.1 | 681 MB | 0.99999988 |
| 32 / 1024 | 50.7 s | 129.6 | 1,100 MB | 0.99999988 |
| **8 / 1024** | **45.1 s** | **145.7** | **474 MB** | 0.99999988 |

**新发现：现状峰值内存接近 6 GB。** 一批 256 条只要混进一条长文本，整批就被补齐到最长那条，注意力张量随之膨胀。
在 16 GB 的机器上这已经是明显的内存压力。TOOLS.md 记录的「后期显著慢于前期」**可能**与此有关（这一点没有验证）。
向量在数值上等价，**改批大小不需要 rebuild 已有索引。**

### 3.6 Rust 对照组（`bench_native.py`，`results/native.json`）

数据：全部消息分片的 778,495 行，每种实现在独立子进程中跑，取 3 次里的最好成绩。

| 实现 | 耗时 | ns/行 | 输出 |
|---|---|---|---|
| Python（项目原函数） | 1.165 s | 1,497 | 基准 |
| Rust 第一版（每行新建 zstd 上下文、中间经过 String） | 1.234 s（同轮 Python 1.125 s） | 1,585 | 一致，**比 Python 慢** |
| Rust 优化版，每行一次调用 | 0.993 s | 1,275 | 一致 |
| **Rust 优化版，每表一次调用** | **0.926 s** | **1,190** | 一致 |
| 跨语言地板：每行一次空调用 | 0.036 s | **47** | — |
| 跨语言地板：整批空调用 | ≈ 0 | 0.0 | — |

- **跨语言调用成本**：每次调用约 47 ns；按批传递列表几乎为零（传的是引用）。
  真正的成本在于返回值必须是 Python 字符串，每行一个 `PyUnicode` 对象，换任何语言都要创建这些对象。
- **收益上限**：全量导出省 0.24 s，占导出时长 0.3–0.7%。即使把导出里全部纯 Python 逐行逻辑（估计 8–10 s）
  都改写成 Rust，按本实验 1.26 倍的加速比推算，也只能省约 2 s。
- **语义一致性**：778,495 行真实数据三种实现输出逐条一致。模糊测试 20 万例
  （非法 UTF-8、正常 / 截断 / 多帧 / 垃圾 zstd 各约 4 万例），值不一致 0 例，报错行为不一致 0 例。

## 4. 兼容性

| 项 | 结论 |
|---|---|
| `sqlcipher3-wheels` 0.5.7（2026-01-07） | macOS 的 arm64 / x86_64 / universal2 都有 **cp38–cp314** 的 wheel；Windows 23 个、Linux 80 个文件；有 sdist。**还没有 cp315 wheel**（项目固定 3.12，不受影响） |
| SQLCipher 版本 | wheel 内置 SQLCipher 4.12.0 / SQLite 3.51.1，CLI 是 4.20 / 3.54。两者读取的 36 个真实库**全部一致** |
| WAL | 快照带上 -wal/-shm；有测试覆盖尚未 checkpoint 的 WAL 行 |
| 异常体系 | 代理层负责翻译；有测试覆盖（`except sqlite3.OperationalError` 能接住） |
| 安全 | 测试证明 tmp 下只有密文快照，退出后清空；密钥错误时报错不回显密钥 |
| 嵌入批大小 | 向量等价，已有索引继续可用 |
| FTS 批量 | 依赖 SQLite ≥ 3.42 的 `secure-delete`（项目的 uv 托管 CPython 3.12 自带 SQLite 3.50.4，满足），重建后配置保留 |
| Rust 扩展 | abi3 wheel 311 KB；但会让本项目从纯 Python wheel 变成**按平台、按架构分别构建**的 wheel |

## 5. 维护成本

| 方案 | 代码量 | 新增工具链 / 依赖 | 隐性成本 |
|---|---|---|---|
| 进程内 SQLCipher | 适配层约 200 行 Python + 约 140 行测试 | 1 个 wheel 依赖 | 第三方 fork 的供应链风险（见 §6） |
| tmutil / 嵌入批 / FTS | 每项十几到几十行 | 无 | FTS 需要持久化的中断标记 |
| Rust 解码 | 125 行 Rust + Cargo.lock（26 个 crate） | rustc + maturin；CI 要构建 arm64 / x86_64 / universal2 多份 wheel；开发时 editable 安装要改用 `maturin develop` | **必须与 Python 语义逐位对齐**（zstd 第一帧、UTF-8 替换规则），否则静默出错；第一版就踩了性能坑（每行新建 zstd 上下文），说明这类代码要持续维护 |

## 6. 风险与局限

- **`sqlcipher3-wheels` 是个人维护的 fork**，上一次发布距今约 10 个月。缓解：`uv.lock` 锁定哈希；保留 CLI 路径作为回退和诊断手段；
  维护停滞时的退路是自建一个很薄的绑定。即使走到那一步，也只是包装库，而不是改写业务。
- **FTS 批量路径的中断安全没有做原型**：导出中途崩溃会留下没有 FTS 的状态。Phase 02 要用 `sync_state` 记标记、重跑时自动补 rebuild，`doctor` 检查一致性，并做故障注入测试。
- **测量局限**：只有一台机器（M3），没覆盖 Intel；运行期间负载 2–9。对比都在同一轮内完成，方向可靠，绝对值有噪声。
- **嵌入的结论来自 8,000 条子集**。全量 68 万条的加速比和内存峰值要在 Phase 02 用一次真实全量构建确认。
- 原型 CLI 是猴补丁接线，**不是可以发布的形态**。

## 7. 对 Phase 02 的建议（按收益与风险排序）

1. **tmutil**：先 `isexcluded`，已排除就跳过（改动约 10 行）。
2. **嵌入批大小**：内部批 8、flush 1024。验收：真实全量构建一次，记录时长和峰值内存。
3. **进程内 SQLCipher**：把原型改成 `decrypt.open_db()`，替换那 5 个调用点；
   CLI 路径保留给 `decrypt` / `inspect` 和回退；新增依赖 `sqlcipher3-wheels`；
   把 spike 里的测试搬进 `tests/`；同步更新 INSTALL（brew sqlcipher 改为可选）和 SECURITY（明文不再落盘）。
4. **FTS 批量路径**：仅用于首次或 `--full` 导出，加持久化中断标记和 `doctor` 检查。
5. **不做**：Rust / PyO3。重新评估的触发条件不变（见 Phase 00 §9）。
