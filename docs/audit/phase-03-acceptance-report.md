# Phase 03：性能验收与技术路线终审

> 日期：2026-11-24 ｜ 基线：`97b78dc`（Phase 00 之前）｜ 被测：`perf/phase00-03` 分支
> 验收脚本：[`spike/phase03/`](../../spike/phase03/)（`acceptance.py` 编排、`probe.py` 在被测版本自己的 venv 里跑）
> 原始数据：`spike/phase03/results/acceptance.json`、`native.json`

## 0. 结论

| 问题 | 结论 |
|---|---|
| 前几阶段的改动是否真带来收益 | **是**。日常路径（冷启动读消息、联系人、检索、增量导出）快 **4–40 倍**；首次导出快 1.8 倍、CPU 减半；向量构建快 6.7 倍、峰值内存从 5.7 GB 降到 0.37 GB；明文不再落盘。三套配置的产物逐字节一致 |
| 有无性能回退 | 有三处小的，均可接受（§4）：`status` 多 ~0.08 s；冷进程常驻内存 +12 MB；8 路并发时中位延迟变高、尾延迟与总耗时大幅下降 |
| 验收中发现的缺陷 | **1 个基线就有的严重缺陷**：多线程同时解码消息正文会报「数据损坏」或**段错误**退出（MCP 后台导出 + 并发工具调用即可触发）。已修复并加回归用例。另有 6 处小问题来自独立审查，均已修 |
| 1. 当前混合语言架构是否合理 | **合理**。项目自己的代码 100% Python；原生代码全部是成熟的第三方 C/C++ 库（SQLCipher、SQLite FTS5、zstd、ONNX Runtime、sqlite-vec），各自负责计算密集的那一段 |
| 2. 是否扩大原生代码 | **不扩大**。复测 Rust 对照：最好的批量形态也只省 1.1 s / 56 s 首次导出（2%），而要付出按平台构建 wheel 与长期语义对齐的代价 |
| 3. 哪些模块保持 Python | **全部**（§6.3） |
| 4. 最值得投入的方向 | ① 向量构建按长度分桶（纯 Python，打掉剩余 padding）② CI 加 CLI 回退后端与 `[semantic]` 缺省两个矩阵项 ③ `sqlcipher3-wheels` 的供应链兜底 ④ MCP 并发读的内存上限（§7） |

## 1. 方法

### 1.1 三套配置

| 配置 | 内容 | 用途 |
|---|---|---|
| `base` | `97b78dc` 用 `git archive` 导出的独立树 + 它自己的 venv | 改动前 |
| `cur_cli` | 当前分支，`AGENT_WECHAT_DECRYPT=cli` | 只含**纯 Python** 改动（tmutil、嵌入批、FTS 批量、zstd 修复） |
| `cur` | 当前分支默认（进程内 SQLCipher + APFS 克隆快照） | 改动后 |

`cur_cli` → `cur` 的差就是**原生扩展本身**（sqlcipher3）的收益；`base` → `cur_cli` 的差是纯 Python 改动的收益。

### 1.2 控制变量

- 三套配置读**同一份冻结源**：微信数据目录的 APFS 克隆（`cp -cR`），用 `paths.db_storage` 指过去。微信在跑、会收新消息，不冻结就比不了产物。
- 每条命令都是独立子进程，套 `/usr/bin/time -l` 取墙钟 / user / sys / 峰值 RSS（含子进程）。
- 另起线程每 5 ms 采样 `HOME/tmp`：峰值占用，以及其中**明文 `plain.db`** 的峰值体积。
- 导出类测试各用一个隔离 `AGENT_WECHAT_HOME`；读取类测试用真实 HOME（已排除 Time Machine，即用户的日常形态）。
- 数据规模：36 个库共约 1 GB，**777,263 条消息**。环境：Apple M3 8 核 / 16 GB。
- **测试期间负载很高（load average 10–14）**，所以绝对值偏慢、噪声偏大。结论只取同一轮内的对比，以及数量级上的差异。
- 不记录任何会话标识和正文：输出只有计数、耗时、内存、摘要哈希。隔离目录、冻结源和基线树都已在结束时删除。

### 1.3 正确性判据

- **索引**：`messages` 全表按 `msg_key` 排序后取 SHA-256；FTS5 `integrity-check`，且 `docsize` 行数等于消息行数；3 条 FTS 触发器都在。
- **读取**：`recent` / `contacts` / `search` 的 stdout 取哈希，三套配置之间比对。
- **解码**：Rust 对照组对全部 77.7 万行比对摘要，另跑 20 万例边界模糊测试。

| | 首次 / 中位 / p90 | 13.9 / 0.61 / 3.91 s | 7.6 / 0.78 / 7.69 s | **1.2 / 0.41 / 0.53 s** |
| 8 线程 × 9 次 | 总耗时 | 65.5 s | 84.3 s | **35.6 s** |

| | tmp 峰值 / 其中明文 | 2.5 GB / 803 MB | 3.3 GB / 1.3 GB | 1.9 GB / **0** |

- cur_cli 在顺序场景里比 base 慢，是负载噪声加上 CLI 后端整库导出的波动，**不是**纯 Python 改动引起的：两者跑的是同一条 `sqlcipher_export` 路径。

## 3. 正确性与稳定性

### 3.1 验收中发现并修复的缺陷：并发解码损坏

- **现象**：8 线程并发读最近消息时，偶发 `zstd decompressor error: Data corruption detected`。压得更紧时，**整个进程段错误**退出。
- **根因**：`reader._ZSTD` 是模块级单例 `ZstdDecompressor`。它派生的 `decompressobj` 共用同一个底层 DCtx，**不是线程安全的**。
- **影响**：MCP 服务把导出跑在后台线程，用户同时发起工具调用就会触发；**基线 `97b78dc` 同样复现**，与解密后端无关。
- **修复**：改为每线程一个解压器（`threading.local`），提交 `ed517db`。
- **回归用例**：`test_zstd_decoding_is_safe_across_threads`。把实现改回单例，这条用例会让进程段错误退出（变异验证）。

### 3.2 导出中途被杀（SIGKILL 整个进程组）

在导出启动后 20 s 和 45 s 两个时点各杀一次，然后重跑：

| 时点 | 配置 | 被杀时已入库 | 被杀时 FTS | tmp 残留明文 | 重跑后 |
|---|---|---|---|---|---|
| 20 s | base | 64,260 行 | 64,260（跟随） | **118.9 MB** | 与一次跑完的索引逐字节一致，FTS 一致，残留已清 |
| 20 s | cur | 258,902 行 | **0**，中断标记 1 | **0** | 同上（标记 → 自动 rebuild） |
| 45 s | base | 364,631 行 | 364,631 | 22.9 MB | 同上 |
| 45 s | cur | 777,263 行（正在 rebuild） | **0**，中断标记 1 | 0 | 同上 |

- 两个时点正好覆盖了 FTS 批量路径的两个窗口：灌库中途被杀，以及 rebuild 进行时被杀。两种情况下次打开都自动补建，结果与一次跑完的逐字节一致。
- 被杀和恢复之间的这段时间里，`doctor` 报「首次导出的 FTS 批量重建被中断」，此时检索只能搜到部分结果。
- 崩溃后不再残留明文，这是进程内后端的又一个安全收益：base 在 20 s 时点残留了 119 MB 明文，要等下一次运行时由清扫器删掉。

  - 门禁 `scripts/check.sh` 通过：import 环、vulture、ruff、pyright、安全扫描，pytest **1,744 passed**。
  - `AGENT_WECHAT_DECRYPT=cli` 下全量 pytest 1,744 passed。

## 4. 回退、重复实现与技术债

| 项 | 判定 | 说明 |
|---|---|---|
| `status` 每次多 ~0.08 s；审查发现它会查两次 `isexcluded` | 小回退，可接受 | 换掉的是其它所有命令上 10 s 的超时；查两次可以合并成一次，未修 |
| 冷进程 RSS +12 MB（60 → 72 MB） | 可接受 | sqlcipher3 动态库 + SQLite 页缓存 |

| 两套解密后端并存（`open_db` 与 `decrypted`） | **有意保留**，不算重复 | CLI 后端是回退路径，也是 `decrypt --out` 的唯一实现；两条路径共用快照与派生密钥（`_keyed_snapshot`），只有最后一步不同 |
| Phase 01 原型（`inproc_sqlcipher.py` 等）与正式实现重复，且已失效 | **已删除** | 只保留 Rust 对照组（`native_decode/` + `bench_native.py`，已改用 `decrypt.open_db`） |
| `open_db` 用 `cast` 冒充 `sqlite3.Connection` | **已修** | 改为窄 Protocol `ReadConnection`：新调用方用到代理不支持的接口时，pyright 会报错 |

| `inspect` 固定走 CLI 后端，没装 brew 就用不了 | **已修** | 改走 `open_db` |
| src 里有注释还在描述明文时代；SECURITY.md 没提派生密钥的内存缓存 | **已修** | |
| CI 只跑默认后端 | **债** | CLI 回退和「没装 `[semantic]`」两种形态只在本地验证过，见 §7 ② |
| `[semantic]` 拆分带来的升级摩擦 | 已在文档中说明 | 不带 `--extra semantic` 的 `uv sync` 会卸掉 fastembed；`doctor` 在「已建索引却没装」时报问题 |
| 代码规模 | 可接受 | src 17,808 → 18,197 行（12 个文件 +539 / −150）；`decrypt.py` 193 → 443 行，增量是第二后端、异常翻译、克隆快照和契约；decrypt / store / export / reader 四个模块的平均圈复杂度 4.31 → 3.71 |

## 5. 「Python 与原生扩展」的实际收益拆分

| 改动 | 性质 | 主要收益 |
|---|---|---|
| tmutil 先查后排 | 纯 Python（3 行） | 每个进程省 10 s：冷启动读取、检索、联系人从 10 s 降到 1 s 以内。**单项收益最大** |
| 嵌入推理批 256 → 8 | 纯 Python（1 个常量） | 向量构建快 6.7 倍、内存为原来的 1/15 |
| FTS 首次批量 | 纯 Python（SQL 编排） | 首次导出 104 → 60 s |
| zstd 每线程一个解压器 | 纯 Python | 修复并发下的损坏与段错误 |
| 进程内 SQLCipher | **第三方原生扩展** | 增量导出 13.3 → 2.6 s；冷读 1.0 → 0.57 s，尾部 4.5 → 0.9 s；MCP 顺序调用快 6 倍；**明文不落盘**、崩溃后不残留明文；不再需要 brew |
| APFS 克隆快照 | 纯 Python（ctypes 调系统调用） | 每次打开分片省 0.1–0.5 s |
| 自研 Rust 解码 | 原生扩展（**未采用**） | 首次导出 −2% |

**收益最大的三项都是纯 Python 改动**，修的是配置错误（超时、批大小）和算法选择（逐行触发器）。原生扩展值得引入的那一项，价值主要在架构层面：明文不落盘，读取代价与所读的数据量成正比，而不是与库的大小成正比。它不是在给某个热循环提速。

## 6. 技术路线终审

### 6.1 当前混合语言架构合理

现状是 **Python 负责编排，成熟的 C/C++ 库负责计算**：

| 计算 | 由谁完成 |
|---|---|
| 页解密（AES / HMAC） | SQLCipher（C） |
| 全文索引 | SQLite FTS5（C） |
| 正文解压 | zstd（C） |
| 向量推理 | ONNX Runtime（C++） |
| 向量 KNN | sqlite-vec（C） |
| 图片解密 | cryptography（Rust / OpenSSL） |
| 语音解码 | pilk（C） |

Python 层负责 schema 适配、异常契约、幂等与断点续传、排除清单、MCP 协议，这些正是需要频繁改动、需要可读性的部分。项目自己维护的原生代码是零行，不需要按平台构建，wheel 仍是 `py3-none-any`。

### 6.2 不扩大原生代码的使用范围

理由：

1. **找不到剩下的热点**。首次导出 56 s 里，Python 解码只占 3 s；增量导出 2.6 s，日常读取 0.57 s。向量构建的耗时在 ONNX 推理里，用 Rust 重写调用层不会更快。
2. **复测的上限只有 2%**（§2.7）。这次复测的 Rust 加速比（1.58×）高于 Phase 01（1.26×），但换算到端到端仍然可以忽略。
3. **代价是结构性的**：要按 平台 × Python 版本 构建 wheel，CI 要带 Rust 工具链，还要和 python-zstandard 逐位对齐「截断帧、多帧、非法 UTF-8」这些边界行为（模糊测试证明能做到，但每次升级依赖都要重新证明）。
4. 本阶段最大的缺陷（§3.1）出在**原生库的线程安全约定**上。原生代码越多，这类「Python 看不见的约定」就越多。

**什么情况下重新评估**：

- 消息量增长一个数量级（约 800 万条），且首次导出里解码占比超过 20%；或者
- 需要在 MCP 进程里做大规模的 CPU 计算（例如本地聚类），且找不到现成的 C 库。

### 6.3 保持 Python 的模块

**全部模块**。下表列出几个乍看可能想换语言的模块，以及不换的理由：

| 模块 | 不换语言的理由 |
|---|---|
| `reader` / `schema` | 跟着微信版本变，可读性和改动速度最重要；计算已在 SQLCipher / zstd 里 |
| `export` / `store` / `migrations` | 本质是 SQL 编排；FTS 批量证明了收益来自换 SQL 写法，不是换语言 |
| `search` / `retrieval` / `vector` | 计算在 FTS5 / sqlite-vec / ONNX 里 |
| `media` / `moments` / `sns_media` | 以 I/O 和格式解析为主，解密已用 cryptography |
| `decrypt` | 已经是对 SQLCipher 的薄封装（异常翻译与资源释放），这一层用 Python 最清楚 |
| `mcp_server` / `cli` / `sync` / `purge` | 协议与流程编排 |

## 7. 后续最值得投入的方向（按投入产出排序）

1. **向量构建按长度分桶**（纯 Python，低风险）。推理批降到 8 后仍有组内 padding；把待嵌入行按 token 长度排序或分桶后再成批，预计还能再快 1.5–2 倍。这是全量耗时最长的环节（约 2–3 小时）。验收方式照本报告 §2.6：同一抽样下比吞吐与向量数值（余弦 ≥ 0.9999）。
2. **CI 补两个矩阵项**：`AGENT_WECHAT_DECRYPT=cli`，以及不带 `--all-extras` 的基础安装。两条回退路径目前只在本地验证过，回退代码最容易在没人注意时坏掉。
3. **`sqlcipher3-wheels` 供应链兜底**。它由个人维护，上次发布约在 10 个月前。现有兜底：`uv.lock` 锁定哈希，保留 CLI 回退，`-m real` 真机对比用例。建议补上：
   - 关注 cp315 wheel 的发布；
   - 预备一份自建 wheel 的方案（上游是 setuptools + 内嵌 amalgamation，构建简单），在上游停更时切换。
4. **MCP 并发读的内存上限**。8 路并发时峰值 RSS 234 MB，tmp 峰值 1.9 GB 密文快照。快照已改成 APFS 克隆，占用基本来自写时复制的元数据。若 Agent 端会高并发调用，可在 `open_db` 外加一个小信号量（例如 4），以中位延迟换取内存上限。
5. **小项**：`status` 合并两次 `isexcluded`；`sync` 在页校验失败时可以在本轮内自动重试一次（目前要等下一轮）。

**不建议投入**：用 Rust 或 C 重写任何自有模块；替换 SQLite FTS5 / sqlite-vec；把 fastembed 换成更重的推理框架。
